**INCIDENTE 2026-07-03 (registrado, correção NÃO iniciada):** a carga de 139M linhas no mesmo servidor (a que fazia 9m46s em faixa única) foi rodada com **partição na PK MD5 CHAR(32)** (modo HEX do #145) + engine server-side → cancelada após 4h sem terminar, deixou **processo pendurado no SQL Server** e o destino ficou com **118M linhas** (resíduo parcial). Causas identificadas no código (não corrigidas): (1) N faixas viram N `INSERT...SELECT WITH (TABLOCK)` **concorrentes** na mesma tabela destino (`ThreadPoolExecutor` em etl_copy_exec.py:933 + TABLOCK em bulk_copy.py:116) → lock X de tabela serializa/bloqueia tudo; (2) fronteiras hex vão **parametrizadas via pymssql**, que interpola str como `N'...'` (NVARCHAR) → conversão implícita da coluna CHAR(32) → predicado possivelmente não-sargável → full scan por faixa (confirmar no plano; depende da collation SQL vs Windows); (3) cancelamento tem granularidade de FAIXA — instrução em andamento NÃO é interrompida (etl_copy_exec.py:568) → sessão fica rodando/rollback longo no banco; (4) autocommit por faixa → faixas concluídas ficam commitadas → resíduo parcial (118M) após cancelar; truncar_antes já tinha zerado o destino. **Workaround imediato**: nesse job, limpar a coluna de partição (ou streams=1) → volta ao caminho de ~10 min; matar/esperar rollback da sessão pendurada. **Correção proposta (pendente)**: engine server-side deve IGNORAR partição (faixa única — o servidor já paraleliza internamente) ou ao menos não usar TABLOCK concorrente; fronteiras hex como literais varchar sargáveis; cancelamento com KILL do @@SPID da faixa.
